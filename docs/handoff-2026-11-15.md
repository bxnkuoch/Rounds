3. Get the model JSON. Either:

### Matterport: API vs SDK
| | Model API (GraphQL) | Showcase SDK |
|---|---|---|
| Where it runs | Server-side (Basic auth, Token ID/Secret) | Browser iframe, `applicationKey` |
| Which models | Only ones our account can access (the CoStar ones) | Any public model, Airedale included |
| Domains | n/a | **localhost only** with our key |

Both expose the same graph. Verified on `7uM5JKssTED`:
- **IDs and edges:** identical sweep IDs; all 644 SDK edges are in the API.
- **Hidden sweeps:** the API had 1 extra sweep that the SDK doesn't show, probably hidden in the tour.
- **Coordinates:** the SDK is y-up at camera height, the API is z-up at floor level. Conversion: `api = (sdk.x, -sdk.z, sdk.y)`, matching to about 7 mm. The exporter already converts to z-up.

Docs to read before touching Matterport code: https://developers.matterport.com/overview/ and https://developers.matterport.com/api/ (also in AGENTS.md).

## What's built

### `tools/matterport_export/` (exporter)
- `serve.py` serves `export.html` on localhost and injects the SDK key from `local.env` at request time, so the key is never written to disk.
- It then receives the export and writes `data/raw/matterport/<model_id>.json`, printing sanity stats (components, asymmetric/dangling links).
- Stdlib only.
- JSON schema v1 contents (z-up, meters):
  - `source`: includes attribution
  - `floors`, `rooms` (bounds; labels are empty in Airedale)
  - `labels`: floor-plan text
  - `tags`: pins
  - `sweeps`: `position` (camera) and `floor_position`, `neighbors`, `enabled`, `placement`

### `backend/app/spatial/nav_graph.py` (loader)
`load_nav_graph(path) -> NavGraph`:
- `nodes`: sweeps with a floor position and `room_id`. Unplaced or disabled sweeps go into `graph.dropped` with a reason; they're never dropped silently.
- `adjacency`: undirected, with weights equal to the straight-line distance between floor positions (in meters, including the vertical component).
- `places`: labels and tags as `Place(id, name, kind, room_id, node_id, …)`, snapped to a node. A place inside a room snaps to a node inside that room.
- `shortest_path(a, b) -> (meters, [node ids])`: A* with an admissible straight-line heuristic. Raises `NoPathError` if there's no path.
- `distance_matrix(ids)`: Dijkstra, the input for OR-Tools. Unreachable pairs are `inf`, and the caller must flag them.
- Also: `components()`, `nearest_node(x, y, floor_id)`, `nodes_in_room()`, `find_places(query)`.

Airedale numbers:
- **Nodes:** 104 in one component; 5 unplaced sweeps dropped.
- **Edges:** 480.
- **Places:** 38 (33 labels, 5 tags).
- **Sample routes:** Nurses Station → Crash Trolley 7.1 m, → Room 1 44.5 m, → Main Entrance 49.0 m.

`backend/pyproject.toml` is minimal: no runtime dependencies yet, pytest in the dev group, managed with `uv`. FastAPI and OR-Tools are **not** added yet.

## Caveats (be honest about these in the demo)

1. **Edges are Matterport's line-of-sight navigation links, not surveyed walking paths.** The median is 7.8 m and the maximum is 57 m (a long corridor). Distances are approximate walking distances.
2. **15 of 38 places sit outside every room's bounds.** These are labels drawn outside the walls, like "Room 1". They snap to the nearest node on the floor, which is usually right but not guaranteed. Checked numerically on 2026-11-15: all 15 snap 2.9–5.2 m from their label (a few seconds of walking), and each "Room N" snaps into a different room. The only shared rooms are Room 14 with "Individual Side Rooms" and Room 16 with "John's Campaign Side Rm", which are adjacent labels. A visual check in the 3D view is still worth doing.
3. **Some labels are area headings:** "Side Rooms (5 - 8)", "Individual Side Rooms", "Assessment Units 1 - 5". "5 Bed Bays with Showers" appears 4 times. Address places by `id`, not by name. Spellings are kept as-is ("Abulatory Care Lounge").
4. **What's real vs synthetic:** the building layout and place names are real (Matterport). Patients, jobs, staff, and any extra labels (individual beds, etc.) must be synthetic and labeled as such.
5. **The 3D viewer only works on localhost** until more domains are added to the SDK key in Matterport Developer Tools.
